# Method and assessment

These are authoring steps, not mandatory HTML sections. Use the project's requested language;
default to English. The SKILL.md map may live in the delivery notes.

1. Define an observable capability and prerequisites. “Predict a conditional request's response”
   is assessable; “understand HTTP” does not bound a task.
2. Link conditions and causes to sources actually read. Choose a minimal case and a contrast.
3. Ask for a prediction before the solution when it discriminates a misconception. Otherwise omit
   it and state why.
4. Work through action → effect → reason without hidden jumps. Place labels beside their elements.
5. Remove one step in a comparable task. Offer an optional hint and explain why each error fails.
6. Ask for justification in a case that changes a condition. Keep the answer hidden until requested;
   later, ask for reconstruction without consulting the page.
7. Check sources and answers; verify design, safety and browser behaviour. Report the three kinds
   of evidence separately.

Sufficient support depends on prior knowledge. Fading worked steps differs from fading concrete
representations. Do not assume “learning styles”, universal memory quotas or that text and a diagram
automatically use two independent sensory channels.

## Branches selected by task

| When | Branch | What to verify |
|---|---|---|
| There is a testable behavioural hypothesis | Predict–observe–explain (POE) | Prediction before reveal; distinguish execution from simulation |
| The goal includes reading, changing and writing programs | PRIMM | Execute cases; do not require making a program for an architecture walkthrough |
| A family of professional tasks spans several lessons | 4C/ID | Whole tasks, conceptual support, procedural information and part-task practice |
| Example, drawing and notation need linking | Concreteness fading | Justify order by prior knowledge; starting abstract may be appropriate |
| A cause needs varying | Explorable explanation | Causal question and checked model; free JS only in the isolated iframe path, with a fallback |
| The question concerns software context and boundaries | C4 | Level that answers the question; a representation, not a teaching method |

## Authoring rubric

Score each dimension 0 (missing/incorrect), 1 (partial) or 2 (sufficient with evidence):
goal/prior knowledge; fidelity/sources; progression; visual function; activity/feedback; transfer/
retrieval; legibility/usability; safety/execution. This is a proposed engineering rubric, not a
validated scale. Fidelity, answers, safety and essential legibility must reach 2; scores elsewhere
cannot compensate for a critical failure.

- **Compliance:** file checks and the exercised path.
- **Teaching quality:** a coherent map and correct answers, reviewed against sources.
- **Measured learning:** real learners' answers, recorded prior knowledge and criteria. Without a
  study, write “learning not measured”. Retention requires a delayed test; clicks cannot replace it.
