Does requesting again mean sending again?

Learn to predict an HTTP validation response. You need to know requests, responses and headers. An ETag identifies a version; If-None-Match makes the request conditional.

Goal: distinguish a GET that reuses a stored copy from an operation that must be rejected. Synthetic cases, reasoned from the standard; these are not executed requests.

Predict before continuing

You stored a representation with ETag "r7". You send GET with If-None-Match: "r7" and the server still has that version. Will you receive 200 with content, 304 or 412? Explain your hypothesis.

Check the prediction

304. The condition requires that no tag match; here one does. On GET, this false condition leads to 304. Choosing 200 ignores the condition; 412 confuses retrieval with other methods.

A worked case

  1. The client sends GET /manual with the tag of its stored copy.
  2. The server compares it with the selected representation, using weak comparison.
  3. Both are "r7": the condition is false. Since this is GET, it responds 304 without content. The stored copy still supplies the content.

The drawing answers one question: which condition chooses between reuse and receiving content? Follow both branches without confusing “false condition” with a server failure.

Scope: an ordinary GET that would otherwise return 200, one tag, no other preconditions or errors. This is not a complete cache implementation.

Complete with less support

The client now holds "r7", but the server has "r8". The same GET carries If-None-Match: "r7". Complete: comparison → condition → response. Try without following the arrows.

A hint

The header name requires that no tag match. What difference does the server's change make?

Check and revise your reasoning

No match → true condition → within this scope, 200 with content. If you chose 304 because a stored copy exists, you missed comparing the current tag. Having a copy is not enough.

Transfer to a write

A PUT sends If-None-Match: * to create /notes/42. A representation already exists. Predict the response and justify why the GET rule does not apply.

Compare against the criteria

The wildcard matches when a representation exists. The condition is false; for PUT, the response is 412 and the operation is not applied. 304 is the GET/HEAD branch. Your justification should include existence, condition and method; just saying “412” does not show the mechanism.

Tomorrow, without consulting: explain why a match can yield 304 in one case and 412 in another. Invent an input that follows the other GET branch.

Check the sources

RFC 9110, §13.1.2 (June 2022) defines the condition and response by method; §15.4.5 describes 304. Sections accessed on 2026-11-03.
